- - **Cryptographic layout and transport serialization mismatches during Ed25519 token integration.**
  - *The Problem:* Custom low-level signing scripts validated cleanly, but tokens generated via `jsonwebtoken::encode` failed against `DecodingKey::from_ed_der()`.
  - *The Catch:* `from_ed_der` acts as a rigid binary scanner that strictly expects standard web metadata parameters like `"typ":"JWT"` in the serialized string header, which default library configurations can omit or format dynamically. Because JWT signatures are derived from the concatenated `HEADER.PAYLOAD` string, this minor structural variance altered the output signature bytes completely.
  - *The Iterative Fixes:* Rectified the backward-compatible path by explicitly forcing type properties in the web handlers (`header.typ = Some("JWT".to_string())`). For true enterprise scale, migrated the startup initialization layer to `DecodingKey::from_ed_components(&pub_b64)` using an unpadded, URL-safe Base64 string. This decoupled the core curve math from rigid, text-based header formatting constraints and eliminated per-request heap allocation overhead entirely during active **20,000 concurrent WebSocket streams**
